这不是协议概览，而是沿着真实源码执行路径逐层拆解： 参数如何进入、广播回调何时执行、payload 如何取产品 ID、xiaomi-ble 返回什么、 状态如何去重、AES-CCM 测试帧如何构造，以及当前实现哪里仍有缺口。

1. 从 main() 开始追调用栈

Python 执行文件后，最底部只做一件事：调用 main()，并把返回值交给操作系统。

if __name__ == "__main__":
    raise SystemExit(main())

main() 的执行顺序是固定的：

build_arg_parser() 只定义 --config 参数，默认读取 config.json。
load_config() 读取 JSON，并校验 MAC、bindkey、超时和 webhook 字段。
JSON 数据转换为不可变的 AppConfig 和 WebhookConfig。
根据 config.verbose 设置日志级别。
asyncio.run(scan(config)) 创建事件循环并进入异步扫描。

JSON 配置怎样变成运行参数

raw = json.loads(path.read_text(encoding="utf-8"))

bindkey_value = _optional_string(raw, "bindkey")
mac_value = _optional_string(raw, "mac")
mac = normalize_mac(mac_value) if mac_value else None
timeout = _number(raw, "timeout", 0.0)

bindkey 直接存放在 JSON 的 bindkey 字段中。 config.json 被加入 .gitignore，避免真实密钥和 webhook 凭据进入版本库。 

return AppConfig(
    mac=mac,
    bindkey=parse_bindkey(bindkey_value),
    adapter=adapter,
    timeout=timeout,
    once=_boolean(raw, "once", False),
    json_output=_boolean(raw, "json", False),
    raw=_boolean(raw, "raw", False),
    verbose=_boolean(raw, "verbose", False),
    webhook=WebhookConfig(...),
)

为什么严格要求 32 个字符

normalized = value.strip().replace(" ", "")
if not re.fullmatch(r"[0-9a-fA-F]{32}", normalized):
    raise ValueError("bindkey must contain exactly 32 hexadecimal characters")
return bytes.fromhex(normalized)

MiBeacon v4/v5 使用 16 字节 key。一个字节由两个十六进制字符表示，因此必须是 16 × 2 = 32 个字符。设备列表里的 24 位 token 不会通过这里。

2. scan() 如何接收广播

scan() 先创建扫描状态和 webhook 任务集合：

stop_event = asyncio.Event()
received_count = 0
webhook_tasks: set[asyncio.Task[None]] = set()
  • stop_event：异步停止信号。超时、Ctrl+C 或配置中的 once 完成时结束扫描。
  • received_count：成功输出过多少条测量，用于决定进程退出码。
  • webhook_tasks：仍在执行的 HTTP POST；退出前会等待它们完成。

Bleak 的回调模型

scanner = BleakScanner(
    detection_callback=on_advertisement,
    **scanner_options,
)

await scanner.start()

BlueZ 每收到一次 BLE 广播，Bleak 就调用一次 on_advertisement(device, advertisement)。 这不是“一台设备调用一次”，而是“一帧调用一次”，所以同一个短帧会连续出现几十次。

回调中的真实顺序

def on_advertisement(device, advertisement):
    nonlocal received_count

    payload = mibeacon_payload(advertisement.service_data)
    if config.raw and payload is not None:
        product_id = mibeacon_product_id(payload)
        if product_id in TARGET_PRODUCT_IDS:
            notice(f"raw {device.address.upper()} {payload.hex()}")

    reading = collector.process(
        build_service_info(device, advertisement, config.adapter or "hci0")
    )
    if reading is None:
        return

    received_count += 1
    print(format_reading(reading, json_output=config.json_output), flush=True)

    if webhook_session is not None:
        task = asyncio.create_task(
            send_webhook(webhook_session, config.webhook, reading)
        )
        webhook_tasks.add(task)
        task.add_done_callback(webhook_done)

    if config.once and reading.temperature is not None and reading.humidity is not None:
        stop_event.set()
--raw 与解析不是二选一。 raw 模式先打印 payload，随后仍然把同一帧交给 Collector 解密解析。

为什么日志和数据分两个输出流

print(f"[mijia-monitor] {message}", file=sys.stderr, flush=True)
print(format_reading(reading, json_output=config.json_output), flush=True)

扫描状态写 stderr，测量数据写 stdout。 因此将配置中的 json 设为 true 后，可以安全地重定向 stdout： 文件里只有机器可读数据，扫描提示仍显示在终端。

Webhook 为什么不会阻塞 BLE 回调

task = asyncio.create_task(
    send_webhook(webhook_session, config.webhook, reading)
)
webhook_tasks.add(task)
task.add_done_callback(webhook_done)

回调只创建异步任务，不等待网络响应，因此慢 webhook 不会卡住当前广播处理。 webhook_done() 负责移除已完成任务并把异常写到 stderr； webhook 失败不会终止蓝牙扫描。 

async def send_webhook(session, webhook, reading):
    async with session.post(
        webhook.url,
        json=asdict(reading),
        headers=webhook.headers,
    ) as response:
        await response.read()
        response.raise_for_status()

aiohttp 的 json= 自动完成 JSON 序列化并设置 Content-Type: application/json。非 2xx 响应由 raise_for_status() 转成异常。

3. 原始广播如何变成产品 ID

先找到 FE95 Service Data

MIBEACON_UUID = "0000fe95-0000-1000-8000-00805f9b34fb"

def mibeacon_payload(service_data):
    for uuid, payload in service_data.items():
        if uuid.lower() == MIBEACON_UUID:
            return payload
    return None

advertisement.service_data 是 dict[str, bytes]。 UUID 字符串先转小写再比较；没有 FE95 就立即忽略。

产品 ID 位于偏移 2..3

def mibeacon_product_id(payload):
    if len(payload) < 4:
        return None
    return int.from_bytes(payload[2:4], byteorder="little")

实测短帧：

10 59  b5 55  7b  85 bf b3 38 c1 a4
│      │      │   └───────────────┘
│      │      │        逆序 MAC
│      │      └─ frame counter
│      └─ payload[2:4] = b5 55
└─ frame control

int.from_bytes(b"\xb5\x55", "little") == 0x55B5

随后用字典完成产品 ID 到型号的映射：

TARGET_MODELS = {
    0x2832: "MJWSD05MMC",
    0x4C47: "MJWSD05MMC",
    0x55B5: "MJWSD06MMC",
    0x5BEA: "MJWSD06MMC",
}
TARGET_PRODUCT_IDS = frozenset(TARGET_MODELS)

frozenset(TARGET_MODELS) 取的是字典的 key，因此等价于不可变集合 {0x2832, 0x4C47, 0x55B5, 0x5BEA}。 不在集合中的小米设备在进入第三方解析器前就被过滤掉。

4. MijiaCollector.process() 逐行发生什么

Collector 是项目自己的核心边界：上游接 Bleak，下游接 xiaomi-ble。

4.1 标准化并过滤 MAC

address = normalize_mac(service_info.address)
if self._target_mac and address != self._target_mac:
    return None

normalize_mac() 同时接受 aa-bb-... 和 AA:BB:...，统一成大写冒号形式。格式不合法直接丢帧。

4.2 过滤协议与型号

payload = mibeacon_payload(service_info.service_data)
if payload is None:
    return None

product_id = mibeacon_product_id(payload)
if product_id not in TARGET_PRODUCT_IDS:
    return None

4.3 每个 MAC 创建一个独立解析器

state = self._states.get(address)
if state is None:
    state = _DeviceState(
        parser=XiaomiBluetoothDeviceData(bindkey=self._bindkey),
        product_id=product_id,
        model=TARGET_MODELS[product_id],
    )
    self._states[address] = state

self._states 的 key 是 MAC。这样同时扫描两台温湿度计时， 每台设备都有自己的帧计数、解密状态和上次测量，不会串数据。

4.4 把整帧交给 xiaomi-ble

update = state.parser.update(service_info)

values = {
    str(key.key): value.native_value
    for key, value in update.entity_values.items()
    if str(key.key) in VALUE_KEYS
}

update.entity_values 不是普通的字符串字典：

  • key 是 xiaomi-ble / sensor-state-data 的设备类 key 对象。
  • key.key 才是 temperature 等逻辑名称。
  • value 是带单位、设备类别等元信息的对象。
  • value.native_value 才是项目最终需要的数值。

项目只保留以下四类：

VALUE_KEYS = ("temperature", "humidity", "battery", "signal_strength")

4.5 解密失败提示的触发条件

if (
    state.parser.encryption_scheme != EncryptionScheme.NONE
    and not state.parser.bindkey_verified
    and not state.encryption_notice_sent
):
    ...

必须同时满足：

  1. 解析器确认该帧使用加密；
  2. bindkey 尚未通过认证；
  3. 这台设备还没有提示过。

encryption_notice_sent 防止每个广播都打印一次错误。 因此短身份帧没有触发提示并不奇怪：它可能根本没有加密对象供解析器验证。

4.6 类型收口

def _number_or_none(value):
    if isinstance(value, bool) or not isinstance(value, (int, float)):
        return None
    return float(value)

Python 中 bool 是 int 的子类，所以必须先显式排除， 否则 True 会被错误转换成 1.0。

5. 哪些代码是本项目写的，哪些交给 xiaomi-ble

职责实现位置具体工作
扫描 BLEBleak与 BlueZ 通信，产生广播回调。
筛选设备本项目FE95、MAC、产品 ID 白名单。
构造输入对象本项目把 Bleak 数据转成 BluetoothServiceInfo。
MiBeacon 帧解析xiaomi-ble识别帧控制、计数器、对象区和加密版本。
AES-CCM 解密xiaomi-ble构造 nonce，验证认证标签，解密对象。
对象 ID 转实体xiaomi-ble例如 3 Mini 的 0x4801 温度、0x4802 湿度。
输出与去重本项目转换为 Reading，过滤重复，打印文本或 JSON。

build_service_info() 是适配器层

return BluetoothServiceInfo(
    name=advertisement.local_name or device.name or DEFAULT_MODEL,
    address=device.address,
    rssi=advertisement.rssi,
    manufacturer_data=advertisement.manufacturer_data,
    service_data=advertisement.service_data,
    service_uuids=advertisement.service_uuids,
    source=source,
)

xiaomi-ble 不是直接接收 Bleak 的两个对象，而是接收 Home Assistant Bluetooth 生态定义的 BluetoothServiceInfo。这个函数只搬运字段，不做协议解析。

实测得到 humidity=74% 的意义很明确： 产品 ID 路由正确、bindkey 与 MAC 匹配、xiaomi-ble 已识别 3 Mini 对象并通过 AES-CCM 认证。

6. 单元测试怎样手工造出 AES-CCM 广播

test_mijia_monitor.py 不需要真实蓝牙。它直接构造 BluetoothServiceInfo，然后调用 collector.process()。

未加密对象区

OBJECTS = (
    b"\x04\x10\x02\xea\x00"  # object 0x1004, len=2, 0x00EA = 234 → 23.4°C
    b"\x06\x10\x02\x37\x02"  # object 0x1006, len=2, 0x0237 = 567 → 56.7%
    b"\x0a\x10\x01\x58"      # object 0x100A, len=1, 0x58 = 88%
)

对象 ID 同样是小端序，因此字节 04 10 表示 0x1004。 温度和湿度整数按 0.1 倍缩放。

加密帧头与 nonce

counter = 1
header = (
    (0x5958).to_bytes(2, "little")
    + (0x2832).to_bytes(2, "little")
    + bytes([counter])
    + mac[::-1]
)

extended_counter = bytes([counter, 0, 0])
nonce = mac[::-1] + header[2:5] + extended_counter

AES-CCM 加密

encrypted = AESCCM(BINDKEY, tag_length=4).encrypt(
    nonce,
    OBJECTS,
    b"\x11",
)

payload = (
    header
    + encrypted[:-4]
    + extended_counter
    + encrypted[-4:]
)

AESCCM.encrypt() 返回“密文 + 认证标签”。测试使用 4 字节标签， 再按 MiBeacon 布局把扩展计数器插入密文和标签之间。 b"\x11" 是附加认证数据（AAD），它不加密但参与认证。

测试边界： 当前 AES-CCM 测试帧使用的是 MJWSD05MMC 的 0x2832 和传统 0x1004/0x1006 对象，不是 3 Mini 原厂固件真实的 0x4801/0x4802 加密样本。

7. 状态、去重与 --once

每个设备当前只保存以下状态：

@dataclass
class _DeviceState:
    parser: XiaomiBluetoothDeviceData
    product_id: int
    model: str
    last_measurement: tuple[float | None, float | None, float | None] | None = None
    encryption_notice_sent: bool = False

去重逻辑

measurement = (temperature, humidity, battery)
if measurement == state.last_measurement:
    return None
state.last_measurement = measurement

RSSI 没放进 tuple，因为 RSSI 每帧都会轻微波动；如果加入 RSSI， 即使温湿度完全没变也会不断输出。

once 配置的停止条件

if config.once and reading.temperature is not None and reading.humidity is not None:
    stop_event.set()

只有同一个 Reading 同时带温度和湿度才停止。 这对一帧包含完整对象的设备成立，但对分帧发送的 3 Mini 不一定成立。

超时与退出码

return 0 if received_count else 2
退出码含义
0至少输出过一条温度或湿度数据。
1扫描器、BlueZ、文件读取等运行错误。
2正常完成或超时，但没有任何有效测量。
130用户按 Ctrl+C 中断。

8. 当前实现的真实缺口

缺口 1：Collector 不会合并分帧测量。 如果先收到 {humidity: 74}，下一帧再收到 {temperature: 27.1}，当前代码会分别生成 (None, 74, None) 和 (27.1, None, None)， 不会自动组合为 (27.1, 74, None)。

因此 3 Mini 上启用 once 可能一直等到超时。正确修复方向是给状态增加最新字段：

@dataclass
class _DeviceState:
    ...
    temperature: float | None = None
    humidity: float | None = None
    battery: float | None = None

# 每帧只覆盖本帧实际出现的字段
if "temperature" in values:
    state.temperature = _number_or_none(values["temperature"])
if "humidity" in values:
    state.humidity = _number_or_none(values["humidity"])
if "battery" in values:
    state.battery = _number_or_none(values["battery"])

# Reading 使用累计后的状态
measurement = (state.temperature, state.humidity, state.battery)
缺口 2：3 Mini 单测只验证“产品 ID 放行与型号映射”。 test_mjwsd06mmc_hardware_revisions() 把传统对象区换上 0x55B5/0x5BEA 头部，并没有复现真实 3 Mini 的加密 0x4801/0x4802 payload。

当前最有价值的 3 Mini 验证来自真实设备：程序确实用正确 bindkey 解出了湿度。 要做完整回归测试，应保存一帧已知密钥的真实温度 payload，并在测试中断言其结果； 测试样本必须使用专用测试密钥，不能提交个人设备密钥。

缺口 3：--raw 不去重。 原厂固件会在一次 burst 内重复发送大量相同短帧，所以 raw 输出刷屏。 这不影响正常模式，只影响排错可读性。

实测短帧为什么没有温度

payload 总长只有 11 字节：2 字节帧控制 + 2 字节产品 ID + 1 字节计数器 + 6 字节 MAC。 头部结束后没有对象区或密文区，所以任何解析器都不可能从这帧得到温度。 必须等待原厂固件数分钟一次的测量 burst。
